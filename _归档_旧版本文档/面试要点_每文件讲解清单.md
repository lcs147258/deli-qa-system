# 面试要点 · 每文件讲解清单

> 用途：面试前过一遍。每个文件三块——**这是什么 / 面试官会问什么 / 我踩过的坑**。
> 原则：**先讲设计取舍，再讲实现细节**。代码是 AI 帮你写的没关系，

## 〇、30 秒项目自述（背熟）

> "这是一个熟食连锁企业的智能问答系统，架构是**双通道**：用户问题先进 FAQ 通道，
> 用 BM25 在 MySQL 问答库里算相似度，超过 0.85 阈值直接返回现成答案，**一次大模型调用都不花**；
> 没命中才进 RAG 通道——先用本地 BERT 做意图分类，通用知识直接让大模型答，专业咨询才走检索：
> **BGE-M3 稠密+稀疏混合检索 → 加权融合 → bge-reranker 交叉重排**，最后拼上下文生成答案。
> 评估上我实测过全链路，FAQ 命中率、意图分类准确率 0.97、检索分类过滤都验证过。
> 业务数据来自真实企业（价目表、产品资料、国标整理稿），食品安全类答案有零幻觉约束。"

## 一、三个必讲的坑（实测发现的课程代码缺陷）

这是整个项目最值钱的部分——**能证明你真跑过、真查过**。

### 坑1：查询侧 fp16 没转 float32（vector_store.py）

现象：检索直接报 `vector type must be the same, field VECTOR_FLOAT, search info VECTOR_FLOAT16`。
根因：GPU+fp16 模式下 BGE-M3 输出 float16；**入库侧转了 float32，查询侧没转**。
教训：**读写的类型转换必须对称**。修复：查询向量同样 `np.asarray(..., dtype=np.float32)`。

### 坑2：流式生成器被当同步字符串用（new_rag_system.py，教育版同样存在）

现象：HyDE / 子查询 / 回溯三种策略**静默失效**——返回"信息不足"但不报错。
根因：`new_main.call_dashscope` 是流式生成器（yield），中间策略却对它调 `.strip()` →
`'generator' object has no attribute 'strip'` → 被 except 吞掉 → 检索返回空。
**只有直接检索那条路是好的**（最终答案生成靠"生成器透传"侥幸工作），课程演示从没暴露。
修复：加 `_llm_text()` 兼容两种注入方式（生成器则拼接、字符串原样）。
**讲法**："我做集成测试时把四种策略逐个跑，才发现三路根本没通——单看代码是看不出来的。"

### 坑4：分类器在"书面语业务问法"上失手（query_classifier）

**现象**：做 RAGAS 评估时发现 4/15 道业务题被判成"通用知识"——生产链路里这意味着
**跳过检索直接让大模型凭记忆答，会幻觉**（"员工健康证有什么要求"没有 FAQ 条目兜底）。
**根因**：训练集里的"专业咨询"几乎都带"你们/你家"这类品牌标记，书面语式的正式问法
（"……有什么要求？""……要做哪些……？"）掉进了通用知识。这是之前修掉"你们捷径"后的**反向副作用**。
**修法**：补 71 条样本，**两类都补书面语**（只补专业咨询会让模型学成"正式措辞=专业咨询"的新捷径），
总量 500 → 571，重训后留出集 **13/15 → 15/15**，验证集 0.96。
**讲法**：这是"数据分布问题"而非模型问题的典型案例——先做分布扫描定位，再定向补数据。

### 坑3：softmax 归一化在同类问题密集时会稀释概率（bm25_search.py）

现象："五香料汁多少钱"与库内问题**几乎一字不差**，却只有 0.583 分（阈值 0.85）未命中。
根因：56 条 FAQ 里 20 多条都含"多少钱"，softmax 概率被同类问题摊薄。
我实测了替代方案：换 top5 softmax 能救回 0.937，**但会把"鸡胗新鲜吗"也放行**（0.922）——
那会答非所问地返回鸡胗的**价格**。
**决策**：维持全量 softmax + 0.85。理由是不对称性——**漏报只是多一次 LLM 调用且 RAG 能答对；
误报是免费但错误的答案**，FAQ 通道必须精确率优先。
**提高命中率的正道是 FAQ 语料运营（每个意图多写几种问法），不是调阈值。**

## 二、逐文件要点

### 1. `base/config.py` —— 配置中心

- **职责**：解析 `config.ini`，向全项目提供统一配置入口；模块级单例 `config`。
- **设计点**：① 配置文件路径用 `__file__` 反推（**不用相对路径**——相对路径是相对 CWD 的，
  换个启动方式就找不到）；② 所有配置项**环境变量优先**（同一份代码换机器只改环境变量或 ini）；
  ③ 编码显式 `utf-8`（文件含中文注释，Windows 默认 GBK 会读挂）。
- **会问**：为什么不用 `os.getenv` 只读环境变量？→ 本地开发用 ini 方便，部署用环境变量，
  两者都支持才不绑环境。
- **坑**：`config.ini` 里**不能写行内注释**（`port = 3307 # 注释` 会让 `int()` 解析失败，
  configparser 不剥行内注释）。

### 2. `base/logger.py` —— 日志

- **职责**：全项目唯一日志配置，控制台 + 文件双输出。
- **设计点**：① `logging.getLogger('DeliRAG')` **单例**——同名返回同一个 Logger，
  这是"全项目一套配置"的基础；② `if not logger.handlers` 守卫**包住全部创建动作**；
  ③ `FileHandler(encoding='utf-8')` 必写（不写用系统 locale，中文日志换环境就乱码）；
  ④ 模块末尾 `logger = setup_logger()` 是**模块级实例**，漏了 `base/__init__.py` 的导入会报
  `ImportError: cannot import name 'logger' from 'logger'`。
- **会问**：Logger 和 Handler 都有 level，哪个生效？→ **两级过滤取更严格的那个**。
- **坑**：这个文件会被加载两次（`base/__init__.py` 把 base 目录加进 sys.path，
  导致既作为顶层模块又作为子模块加载）。**没有守卫时 handler 会变成 4 个、日志打两遍**——
  实测过。守卫不是"防御性编程的礼貌"，是这里真的会踩。

### 3. `mysql_qa/utils/preprocess.py` —— 分词

- **职责**：BM25 的语料和查询统一走这一个分词函数（**口径必须一致**）。
- **设计点**：`jieba.lcut(text.lower())` + **注册熟食领域自定义词**
  （虎皮鸡爪、八大拌、五香料汁、效期、报损、冷链……）——
  不注册的话"虎皮鸡爪"会被切成"虎皮/鸡/爪"，BM25 的词项统计就没意义了。
- **会问**：为什么不用 BERT 分词？→ BM25 是词袋模型，要的是词级统计；
  中文分词质量直接决定召回。
- **迁移点**：**换了领域，分词词典也要跟着换**——这是迁移时最容易漏的一步。

### 4. `mysql_qa/db/mysql_client.py` —— FAQ 数据访问

- **职责**：连接 / 建表 `faq(category, question, answer)` / CSV 导入 / 查询问题列表与答案。
- **设计点**：① `charset='utf8mb4'`（utf8 三字节存不了部分字符）；② 参数化查询 `%s`
  （防注入 + 处理答案里的引号）；③ 导入前判断条数**幂等**；
  ④ 读 CSV 用 `encoding='utf-8-sig'`（文件带 BOM，普通 utf-8 读会让第一个列名带 BOM 而取不到值）。
- **会问**：为什么用 pandas 不用 csv 模块？→ 数据量小、写法短；工程上纯 csv 模块更轻。
  诚实回答即可，重点是你知道两者差异。
- **坑**：`fetch_answer` 要判 `None`（问题被删过时 fetchone 返回 None，取 [0] 会崩）。

### 5. `mysql_qa/cache/redis_client.py` —— 缓存

- **职责**：Redis 读写 + 答案缓存 `get_answer` / `set_data`。
- **设计点**：① **缓存键带 `deli:` 前缀**——与教育版共用同一个 Redis 实例，
  不加前缀两个项目互相覆盖语料缓存，表现为"换了 FAQ 检索回来还是旧题"，**不报错，极难排查**；
  ② `decode_responses=True` 免手动解码；③ **读写序列化必须对称**：
  `set_data` 用了 `json.dumps`，`get_answer` 就必须 `json.loads`——
  否则命中缓存时答案带着 JSON 转义，**同一个问题第二次问格式就变了**（教育版真实踩过）。
- **会问**：缓存穿透/雪崩怎么办？→ 本项目是问答场景，高频问题是重复问同一批，
  key 数量有限；真要做可以加空值缓存 + 随机过期时间，但当前规模不需要——**讲清楚为什么不必要**。

### 6. `mysql_qa/retrieval/bm25_search.py` —— FAQ 通道核心 ★

- **职责**：语料加载（Redis 优先→MySQL 回填）、BM25 打分、softmax 归一化、阈值判定、答案缓存。
- **设计点**：① **Cache-Aside + Lazy Loading**：首次启动从 MySQL 加载问题库、jieba 分词后回填 Redis；
  ② **softmax 归一化**把无上限的 BM25 原始分转成概率分布，才能跟 0.85 这种阈值比较
  （减最大值防溢出）；③ 返回 `(answer, need_rag)` 二元组：命中→`(答案, False)`，
  未命中→`(None, True)` 交给 RAG；④ **任何异常都降级为"走 RAG"**，不让 FAQ 拖死系统。
- **会问**：BM25 和向量检索什么区别？→ BM25 是**词项级**统计（稀疏、精确、不懂语义），
  向量是**语义级**（懂同义改写但可能"理解过头"）。这也是为什么要混合检索。
- **必讲坑**：见「坑 3」——softmax 稀释 + 我的替代方案实测与否决理由。

### 7. `mysql_qa/main.py` —— FAQ 通道调试入口

- **职责**：把 MySQL + Redis + BM25 组装成可独立运行的交互式问答，方便单通道调试。
- **设计点**：模块化分层——`main.py` 只做组装与展示，逻辑都在下面三个文件里。
- **会问**：为什么单独有个 main？→ **模块级自测**是工程习惯：不启动整个系统就能验证一个通道，
  排查时能快速定位"是 FAQ 坏了还是 RAG 坏了"。

### 8. `rag_qa/core/prompts.py` —— 提示词模板

- **职责**：4 个模板：`rag_prompt`（生成答案）/ `hyde_prompt` / `subquery_prompt` / `backtracking_prompt`。
- **设计点**：**模板本身领域无关**——迁移熟食域时 4 个模板一个字没改。
  领域差异只在 `rag_prompt` 的兜底话术（信息不足转人工客服）和测试代码里。
- **必讲点**：`rag_prompt` **必须用 4 变量版**（context / **history** / question / phone）。
  课件正文展示的是 3 变量简单版，如果照抄，上层 `format(history=...)` **不报错**
  （多余 kwarg 被 `str.format` 静默忽略），但多轮对话历史永远进不了 prompt——
  **不报错的功能失效，最难查**。

### 9. `rag_qa/core/document_processor.py` —— 父子分块

- **职责**：目录递归加载（PDF/Word/PPT/图片OCR/Markdown）→ 父块 1200 → 子块 300 → 挂父块信息。
- **设计点**：① **`source` 元数据 = 目录名去掉 `_data` 后缀**——它一路传到 Milvus 的 source 字段，
  支撑前端分类过滤，**所以目录名必须与 config 的 valid_sources 严格一致，拼错过滤会静默失效**；
  ② `.md` 用 Markdown 专用切分器（保标题层级），其它用中文递归切分器；
  ③ 每个子块的 metadata 挂 `parent_id` + `parent_content`，这是后面"检索子块、生成用父块"的前提。
- **会问**：为什么父子分块？→ 子块小，向量匹配准；父块大，喂给大模型的上下文完整。
  **两个目标各取所长**——这是当前 RAG 的主流解法之一。

### 10. `rag_qa/core/vector_store.py` —— 混合检索核心 ★★（最重要）

- **职责**：BGE-M3 编码 → Milvus 建集合/入库 → 混合检索 → 父块去重 → 交叉重排。
- **四个必讲设计点**：
  1. **混合检索 + WeightedRanker(1.0, 0.7)**：稠密管语义（"卤味坏了"能匹配"食品变质"）、
     稀疏管关键词（"GB 31654"这类编号精准命中），权重明确所以用加权；
     **权重说不清或融合三路以上异构检索器时才换 RRF**（RRF 按排名融合，不需要分数可比）。
  2. **检索子块 → 映射父块 → 父块层面重排 → 取 Top-M**：
     重排要和最终输出粒度一致（选的是"哪几段话给大模型"）。
  3. **父块少于 2 个时跳过重排**——排序没意义，省一次模型推理。务实的小优化。
  4. **CrossEncoder 与双塔的区别**：双塔(embedding) query 和 doc 分别编码、可离线建索引，快但粗；
     CrossEncoder 把 query+doc 拼一起过模型、能建模交互，准但只能对少量候选逐对算——
     **这就是为什么必须两阶段：召回求快求全、重排求准**。
- **必讲坑**：见「坑 1」（fp16 读写不对称）。另外 `sorted(zip(scores, docs))` 在**两条得分完全相同时**
  会去比较 Document 对象直接抛 TypeError——**只在恰好平分时触发，极隐蔽**，必须写 `key=lambda pair: pair[0]`。

### 11. `rag_qa/core/query_classifier.py` —— 意图分类

- **职责**：bert-base-chinese 微调二分类（通用知识 / 专业咨询），含完整训练代码（Trainer + 8:2 切分）。
- **设计点**：① **为什么用小模型不用大模型做路由**：本地推理几十毫秒、零 token 费用；
  大模型路由一次 1-2 秒还花钱。二分类边界清晰，小模型够用——**这是成本/延迟取舍，要主动讲**；
  ② 标签名沿用"通用知识/专业咨询"，`label_map` 代码不用动；
  ③ 设备自动选择；④ 推理 `torch.no_grad()`。
- **实测数据**：500 条训练集，**验证集准确率 0.97，训练 10.5 秒（3060 Ti）**。
- **诚实点**：有一条已知边界失手（"帮我想个朋友圈卖卤味的文案"被判专业咨询）。
  面试主动说比被问出来好，顺带讲你打算怎么补（补同类负样本）。
- **数据质量故事（加分项）**：训练集生成后我做分布扫描发现——**通用知识里含"你们"0 条、
  专业咨询 333 条**，分类器会学成"见'你们'就判专业咨询"的捷径（训练准确率虚高、上线翻车）。
  修复：专业咨询 180 条去前缀改写 + 通用知识补 7 条天然含"你们"的闲聊（天气/节令类）。
  **结论：生成式造数据，数字全对 ≠ 数据没病，要做分布扫描**。

### 12. `rag_qa/core/strategy_selector.py` —— 策略路由

- **职责**：让大模型在 4 种检索策略里选一种（直接 / HyDE / 子查询 / 回溯）。
- **设计点**：这个 prompt 的输出**要被代码解析**（`if strategy == "子查询检索"`），不是给人看的，
  所以必须：① 严格约束输出（"直接返回策略名称，不要输出分析过程"）；
  ② **低温 temperature=0.1**（路由要稳定不要创造）；③ **必须兜底**（调用失败返回"直接检索"，
  最便宜最安全的默认路径）；④ **few-shot 示例就是分类边界的定义**——教育版的示例是
  "AI学费/JAVA大纲"，熟食版换成卤味问法，这是本项目迁移时改动的**唯一一处提示词**。
- **会问**：这几次 LLM 调用？→ 见下表。

### 13. `rag_qa/main.py` —— RAG 通道入口

- **职责**：两种模式——`--data-processing` 入库（遍历 5 个知识目录 → 切分 → 向量化 → Milvus）；
  默认交互式查询。
- **设计点**：① 入库前**确保 Milvus 库存在**（`db_name='deli'` 在库不存在时 MilvusClient 会直接报错，
  所以要先在默认库上建出来）；② 数据目录默认值基于 `__file__` 推导，不受 CWD 影响；
  ③ 单目录失败不中断整体入库。
- **坑**：`python rag_qa/main.py` 直接运行时 `sys.path[0]` 是 rag_qa/ 而不是项目根，
  必须手动把项目根插进 sys.path，否则 `from base.config` 报 ModuleNotFoundError。

### 14. `init_faq_data.py` —— 数据初始化

- **职责**：建库 `deli_qa` + 建表 + 导入 CSV + 验收打印。幂等可重复执行。
- **设计点**：`CREATE DATABASE` **不能参数化**，所以先用不带库名的连接建库；
  导入前查条数，已有数据就跳过（防止重复执行把 FAQ 翻倍）。

### 15. 课程提供、但你要能讲的三个文件

| 文件 | 讲什么 |
|---|---|
| `new_main.py` | **顶层编排**：先 FAQ（BM25 0.85）→ 命中直接返回、否则交 RAG；会话历史（最近 5 轮）；`yield` 流式。**我在这里加了 httpx 修复**：`max_keepalive_connections=0`，禁用连接复用——服务闲置后连接池里的陈旧连接会让首次请求卡 40 多秒，实测修复后稳定 1 秒级 |
| `rag_qa/core/new_rag_system.py` | **RAG 编排**：BERT 分类 → 策略选择 → 检索 → 拼上下文 → 生成。**必讲**：`_llm_text()` 是我加的（见坑2）；子查询分支 N 个子查询 = N 次完整检索+重排，延迟线性增长，所以只在多实体问题上走 |
| `app.py` | **Web 层**：FastAPI + WebSocket 流式（`start/token/end`）+ 固定问候语正则 + 会话管理 + `/api/sources` 动态给前端提供知识分类下拉框 |

### 16. `static/index.html` —— 前端

- **职责**：聊天界面、知识分类下拉（**从 `/api/sources` 动态加载**，不是硬编码）、快捷回复、历史展示。
- **会问**：分类过滤怎么实现的？→ 前端选中分类 → 请求带 `source_filter` →
  `app.py` 透传 → `new_rag_system` → `vector_store` 拼成 Milvus 过滤表达式
  `source == 'safety'` → 检索时生效。**注意必须是完整布尔式，只传 `safety` 会报
  "predicate is not a boolean expression"**。

## 三、高频追问速查

### LLM 调用次数（成本视角）

| 路径 | 调用次数 |
|---|---|
| FAQ 命中（BM25 ≥ 0.85） | **0 次** |
| 通用知识（BERT 分类短路） | 1 次（直接作答） |
| 专业咨询 → 直接检索 | 2 次（策略选择 + 生成） |
| 专业咨询 → HyDE / 回溯 | 3 次（+ 生成假设答案/简化问题） |
| 专业咨询 → 子查询 | 3 次 LLM + N 次检索（N=子查询数） |

**讲法**："架构是围绕省调用设计的：FAQ 零调用、意图分类用本地 BERT 零成本做路由、
只有真正需要资料的专业咨询才付出 2-3 次调用。策略选择那次很便宜（低温、只回几个词），
生成那次是成本大头。"

### "为什么不用 LangChain / LangGraph？"

> "检索链路我直接调 pymilvus 和 openai SDK，只借用了 langchain_core 的 Document 统一数据结构。
> 检索是性能和可调试性的关键路径，我要它完全透明——套编排框架后出问题要先进框架内部定位，
> 而且版本迭代带来不确定性。这个项目是固定 pipeline（分类→策略→检索→生成），
> 顺序确定、没有需要动态规划的循环，用 LangGraph 属于过度设计。"

### 数据合规（主动讲，显专业）

食品安全类问题**零幻觉容忍**：答案只能来自知识库，rag_prompt 的"信息不足转人工"兜底必须保留；
价格政策类标注时效"以门店当日公示为准"；**内部配方属商业机密绝不入库**
（否则顾客问"你们黄瓜怎么拌的"就能套出秘方）——**这条能自然引出"角色权限+知识隔离"的架构演进方向**。

### 性能数字（要能背）

- 冷启动：`import torch` 12.7 秒 + BGE-M3 加载 11.3 秒；**稳态查询编码 0.05 秒**
- 分类器：500 条训练集，GPU 训 10.5 秒，准确率 0.97
- FAQ 命中相似度：0.906 ~ 0.994
- 知识库：36 个子块 / 5 类知识；FAQ 56 条
- **RAGAS 四指标**：precision 0.933 / recall 0.800 / faithfulness 0.803（排除拒答类 0.889）/
  relevancy 0.796（排除拒答类 0.920）——要能解释"为什么 faithfulness 不是 0.9+"（见评估报告第三节·发现3）
