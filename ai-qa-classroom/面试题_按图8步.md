## 〇、开场自述

### ★ Q0. 用 1 分钟介绍这个项目

**答题骨架**



* 是什么：面向**加盟商和终端顾客**的熟食连锁智能问答系统，回答产品规格价格、加盟批发政策、食品安全储存、冷链配送四类问题

* 本质：一条**确定性流水线**（不是 Agent 自主决策）—— 路由全由规则 / 小模型 / 阈值决定，LLM 只干三件事：选检索策略、改写问题、照知识库写答案

* 链路一句话：**FAQ 热路径秒答 → BERT 辨意图 → LLM 选策略 → pgvector 稠密 + pg_search 稀疏双路召回（SQL 内 RRF 融合）→ CrossEncoder 精排 → 置信度闸门 → DeepSeek 照书生成 → MySQL 记会话**

* 第二版轻量化：检索层是 **ParadeDB 单容器**（一个 PostgreSQL 同时跑 pgvector 和 pg_search，替代 Milvus+etcd+MinIO 三件套），embedding/reranker 各有**本地模型 / SiliconFlow 云 API 双后端**，整套系统 2核4GB 服务器纯 CPU 可部署

* 三个设计取向：**成本省**（FAQ 命中零 LLM 调用）、**安全收**（低置信拒答不硬编）、**检索分策略**（不同问题走不同检索路径）

## 第 1 步・你举手提问（接入层）

### ★ Q1. 为什么同时提供 REST 和 WebSocket 两种接口？



* REST 处理非流式请求、健康检查、历史查询；**WebSocket 承载流式问答**（`api/v1/qa.py`，协议帧 `start / token / end`）

* 流式的价值：答案逐字蹦出来，首字延迟低，长答案用户不用干等；客服场景体感好

* 追问 "为什么不用 SSE"：SSE 只能服务端单向推，WebSocket 双向、后续好扩展（如中断、客户端事件）

### ★ Q2.（踩坑）同步的模型推理怎么不卡死 WebSocket？



* **坑**：早期在 async 端点里直接调用同步的模型推理 / LLM 生成 → 阻塞 uvicorn 事件循环 → 心跳不响应 → 客户端约 40s 超时断开；**表现为 "连接断了" 而不是报错**，一开始会误查 WebSocket

* **解**：所有同步重型调用（BGE 编码、rerank、BM25、MySQL）一律 `asyncio.to_thread` / `run_in_executor` 丢线程池（`service.py` 全文统一此模式）

* 教训：async 端点里直接跑同步阻塞函数，等于把整个服务的吞吐押在它不阻塞上

## 第 2 步・先翻 "熟客问答本"（FAQ 热路径）

### ★ Q3. 为什么不直接向量检索，要在最前面加 FAQ 通道？



* 热路径目标是**成本和延迟**：BM25 毫秒级、零模型推理、零 LLM 调用；答案是人工审过的标准答案，可控

* 架构：MySQL 存 96 条问答对、Redis 做缓存（`deli:` 前缀隔离），`rank_bm25` + jieba 领域词分词（`faq/`）

* 命中阈值 **0.85** 直接返回；未命中才进入后面的 RAG

### ★ Q4. BM25 原始分无界、还随语料规模漂移，0.85 的固定阈值凭什么能用？



* 关键：**不是直接用 BM25 原始分，而是对一次查询的所有问题分数做 softmax 压到 \[0,1]**（`bm25_search.py:58-61`）

* softmax 后阈值是 "相对最匹配问题的置信度"，96 条和 500 条语料下含义一致

* 追问 "softmax 对候选集敏感吗"：敏感，语料里强干扰项多会拉低峰值 —— 所以更要靠语料运营给每个意图补多种问法

### Q5. 阈值为什么定到 0.85 这么高？



* **误报和漏报代价不对称**：误报 = 免费但错误的答案；漏报 = 只是多一次 LLM 调用、RAG 还能答对

* 所以 FAQ 必须**精确率优先**，阈值宁高勿低

* BM25 是纯词汇匹配，"鸡胗新鲜吗" 和 "鸡胗多少钱" 共享词项，靠高阈值压住误命中

### Q6. Redis 具体缓存了什么？Redis 挂了呢？



* 缓存四类：原始问题语料、分词后语料（启动加载 BM25 用）、高频 query 的答案（`bm25_search.py`），以及第二版新增的 **embedding 内容哈希缓存**（key 为文本 sha256，`deli:embed:{后端}:{hash}`，同一句话不重复调云 API；进程内 dict + Redis 两层）

* Redis 挂 → 退化为直查 MySQL、embedding 直连模型/API，只是慢和费额度；MySQL 挂 → FAQ 通道整体下线，直接走 RAG

## 第 3 步・小管家辨一辨意图（意图分类）

### ★ Q7. 意图判定为什么 "规则在前、BERT 在后"，顺序反过来不行吗？



* 实际是三层：**闲聊精确词表 / 关键词 → 业务专业关键词 → BERT 二分类**（`service.py:56-77`）

* 业务关键词（多少钱、保质期、冷链、加盟…）命中**直接判定专业问题，不给 BERT 翻盘机会**

* 原因：食品安全场景下两种错误代价不对称 —— 判成 "通用知识" 会让模型用自身记忆硬答（危险）；判成 "专业问题" 只是多一次检索（安全）

* 规则还能省推理、零延迟、可解释；BERT 只在规则都没命中时兜底

### Q8. BERT 分类器什么架构？怎么训练的？



* `bert-base-chinese` 微调的**二分类**：general 通用 /specialized 专业（`core/query_classifier.py`，权重在 `models/classifier/bert_query_classifier`）

* 训练集 500 条：LLM 按领域提示词生成 + 两轮人工质检（`scripts/train_classifier.py`）

* BERT 判 "通用" 要求概率 **≥ 0.85**（`GENERAL_MIN_PROB`），低于此仍按专业走 RAG

* 修过一个 "捷径学习"：训练集通用类里特意补含 "你们" 的闲聊，否则模型会学成 "含 ' 你们 '= 专业咨询"

### Q9. 分类器加载失败 / 推理异常怎么办？



* `classify_query()` 捕获异常 → **降级为 specialized**（走 RAG 是安全方向），不阻断主流程（`query_classifier.py:71-77`）

## 第 4 步・选条找书的路子（策略选择）

### ★ Q10. 四个检索策略分别解决什么问题？各举一个例子



* **DIRECT 直接**：短事实问题，原问题直接检索（"酱鸭多少钱一斤"）

* **HYDE 假设文档**：问题模糊 / 口语化，先让 LLM 写一段 "假设答案"，用假设文档去检索（"这个没看懂啥意思"）

* **SUBQUERY 子查询**：宽泛大问题拆成 3 个子查询并行检索再合并（"你们加盟都有啥支持"）

* **BACKTRACK 回溯**：太具体的问题先拔高成基础问题（Step-back），再检索（具体现象 → 背后的通用规范）

### Q11. 为什么让 LLM 四选一？什么情况下不花这次调用？



* 规则快判前置（`strategy_selector.py:42-50`）：≤12 字且含事实词（多少钱 / 营业时间 / 地址…）直接 DIRECT；≤10 字且含 "没懂 / 啥意思" 直接 HYDE

* 其余才让 LLM 选，返回中文策略名再归一化；**任何异常兜底 DIRECT**—— 检索链路永远可用

### Q12. HyDE 什么时候会帮倒忙？



* 多一次 LLM 调用（延迟 + token）；假设文档方向跑偏会把整个检索带偏

* 所以实现里失败必回退原问题；且知识库没有对应主题时，假设文档再好也检不到东西 —— 此时如实转人工，是**数据缺口不是链路故障**

## 第 5 步・小猎犬混合找书（混合检索 + 父子分块）

### ★ Q13. 为什么 dense 和 sparse 双路？各自擅长什么？



* **Dense（512 维本地 bge-small-zh / 切云端后 1024 维 bge-m3）**：语义匹配，"能放多久" ↔ "保质期" 能对上；但对专有名词、数字、国标号容易糊

* **Sparse（pg_search 的 BM25）**：这次稀疏路用的是**真 BM25**——ParadeDB 的 pg_search 扩展在 PG 内建倒排索引，中文用内置 **Lindera 分词器**；字面命中强，桶子鸡、五香料汁、GB 31605 这类专有词命中好，但不懂同义改写

* 两者失效模式互补，双路是为了覆盖单路盲区，不是 "双路必然更好"

* ⚠️ 易被追问 "稀疏是不是 BM25"：**第二版是**（pg_search BM25）；FAQ 通道的 rank_bm25 也是 BM25，但一个是库内倒排索引、一个是 Python 内存语料，两套独立

### ★ Q14. 双路分数量纲完全不同（cosine 相似度 vs BM25 分），怎么融合？



* 用 **RRF（Reciprocal Rank Fusion，k=60）**：`score = Σ 1/(60 + rank)`，**只看每路里的排名、不看原始分**，天然免疫量纲问题——这正是选它的原因：cosine 和 BM25 分数尺度没法直接对齐，硬加权必然被数值大的一路绑架（`core/fusion.py`，可插拔另有 weighted_rrf 0.6/0.4 与 CombMNZ）

* 融合**下推成一条 SQL**：dense CTE（HNSW 取 top50）+ sparse CTE（BM25 取 top50）`FULL OUTER JOIN USING(id)`，在库内算好 RRF 只返回 top10（`knowledge_base.py` 的 `_dense_lane / _sparse_lane / hybrid_search`）

* RRF 的取舍：零参数、免标定、跨后端稳定（换 embedding/rerank 模型融合层都不用动）；代价是只表达 "都靠前的更优先"，表达不了固定权重偏好，所以另留了 weighted_rrf 实现做对比实验

* 诚实：第一版用 Milvus WeightedRanker(0.7,0.3)，框架内部 arctan 归一化；脱离 Milvus 后权重先验没法干净实现，RRF 是更稳的选择，权重策略留作后续实验

### Q15. 为什么换 ParadeDB？双路检索在库里长什么样？



* **一个 PostgreSQL 容器替代 Milvus+etcd+MinIO 三件套**：运维面从 3 容器变 1 容器、一份备份、一个事务体系；目标部署机只有 2核4GB，跑不动 Milvus 全家桶。镜像锁版本 `paradedb/paradedb:0.25.11-pg17`

* 索引：dense 列是 `vector(512/1024)`，建 **HNSW（`vector_cosine_ops`，m=16、ef_construction=256）**；稀疏侧 `CREATE INDEX ... USING paradedb (id, (content::pdb.lindera(chinese))) WITH (key_field='id')`，dense 相似度用 `1 - (embedding <=> $1)`

* 踩过的真实坑（pg_search 0.25 语法和网上旧文档完全不同，值得讲）：
  ① schema 是 **`pdb`** 不是 paradedb；② 0.25 已没有 `create_bm25` 存储过程，改用 `USING paradedb` 建索引；③ `content @@@ '冷藏温度'` 默认按**相邻短语**匹配导致 0 命中，必须构造 `boolean(should => ARRAY[term('content','冷藏'), term('content','温度')])` 做 bag-of-words OR；④ 查询词要先在库内 `SELECT '冷藏温度'::pdb.lindera(chinese)::text[]` 用同一分词器切，保证入库/查询一致

* 代价：语料规模上限不如专用向量库（HNSW 内存占用 + PG 单机），82 块的当前规模下零压力，上到百万级要重新评估分片

### ★ Q16. 父子分块（Small-to-Big）解决什么问题？



* 矛盾：**小块向量命中精准，但喂给 LLM 上下文不完整；大块上下文完整，但向量召回不精准**

* 做法：子块 300 字参与向量编码 / 召回，每个子块冗余携带 `parent_content`（父块 1200 字）；子块命中后 `knowledge_base.py` 的 `promote_to_parents()` 去重回升父块，再对父块精排、把父块全文喂 LLM

* 一块多子块命中只保留召回分最高的，天然去重

* 一句话：**用小块找得准，用大块答得全**

## 第 6 步・精挑细选把好关（精排 + 置信度闸门）

### ★ Q17. 为什么还要 CrossEncoder 精排？双塔的召回分不够用吗？



* 双塔召回模型（bge-small-zh / bge-m3）query/doc 各自独立编码，没有 token 级交互，快但精度有限，适合**召回求快**

* CrossEncoder 把 query+doc 拼接后一起过模型，交叉注意力看得深，**精排求准**；代价是每对一次前向，所以只对召回候选做。双后端可切：本地 `bge-reranker-large`（2GB 权重、GPU/CPU 可跑）或 SiliconFlow `bge-reranker-v2-m3` 云 API（服务器零内存占用，`core/reranker.py`）

* 输出相关性分，取 top-3；低于 **0.05** 的视为召回噪声直接丢弃

* **云端精排故障降级**：超时 / 429 / 鉴权失败时不阻断链路，按 RRF 召回排名映射 0.5~0.85 的兜底分顶上（日志 `reranker.sf_failed_degrade_rrf`）——可用性优先，日志里留痕便于事后发现

* 细节：输入截断防超出模型 max\_length

### ★ Q18. 0.45 的置信度阈值怎么来的？



* 精排 top1 分数即 confidence：**≥ 0.45** 走 RAG 生成；**< 0.45** 走固定话术转人工，完全不调 LLM

* 阈值做过**经验标定（不是拍脑袋，但也不是标注集）**：4 道标准题 + 8 道边界/域外题在两个后端上各跑一遍。本地 large：高置信题 0.9557/0.9677/0.4687，红线题 0.1024；云端 v2-m3 分数更极化——相关题 0.82~0.98、擦边题 0.11~0.30、域外/配方套取全 0.00，0.45 正落在 0.30~0.52 的空当里，12 题判定全部符合预期，所以沿用 0.45 不调

* 诚实说法：这是小样本探针标定，**还没有人工标注集**；正式标定应攒一批 "可答/不可答" 标注 query，画分数分布取两峰之间的谷。换 reranker 后端必须重标（v2-m3 和本地 large 分数尺度不同，这也是配置里专门留注释的原因）

* 已知不足：闸门只看 top1 分数，还没校验 "检回内容是否含问题关键实体"

### ★ Q19. 低置信为什么不让模型 "谨慎地答并说明"，而要直接转人工？



* 场景特殊性：保质期、留样温度、中心温度这类问题，模型 "谨慎地猜一个" 仍可能错，而用户会当标准去执行

* 所以宁可拒答；固定话术给人工电话，**不调 LLM = 食品安全零幻觉**

* 拒答不是终点：问题自动入 `pending` 待补充队列，变成知识库的待补清单 ——**数据飞轮的起点**

### Q20. SUBQUERY 策略三路结果怎么合并？



* 3 个子查询各自召回 + 回升父块，`asyncio.gather` 并行；父块按内容去重、保留最高分；最后对原问题**统一做一次父块精排**（`reranker.rerank_parents()`）

## 第 7 步・博学老师照书讲（答案生成）

### ★ Q21. 怎么保证答案不幻觉？



* 四道保险：① 提示词要求**严格只依据给定 context、无依据就明说**；② **温度 0**；③ 答案末尾**强制附参考来源**（`📚 参考来源`，去重列出 source\_name）；④ 低置信在生成前就被闸门拦下

* 价格 / 保质期类主动注明 "以门店当日公示为准"

* LLM 自身故障（鉴权 / 限流 / 超时）也有 fail-safe：捕获后转人工话术，不向前端抛技术错误

### Q22. 流式时怎么保证中间 LLM 调用（HyDE / 子查询改写）不泄给前端？



* 流水线里**只有最终生成节点把 token 放进队列**，改写 / 策略 / 分类的 LLM 调用结果只写内部上下文、不入 token 队列（`service.py:447-457`），天然隔离

* 来源后缀在流结束后才拼到答案尾部

### Q23. 食品安全红线具体有哪几条？



* 内部配方 / 成本 / 供应商底价：提示词禁止泄露 + 物理不入库（见 Q29）

* 保质期、温度、留样义务：绝不靠模型记忆回答，低置信转人工

* 价格时效：标注为指导价、以门店公示为准



***

## 第 8 步・老师的小本本（会话记忆）

### ★ Q24. 多轮记忆怎么做的？为什么只留 5 轮、为什么不做摘要压缩？



* 跨请求以 **MySQL&#x20;**`conversations`**&#x20;表**为准，每条出口（FAQ / 寒暄 / RAG / 转人工）都落库；提问时取最近 **5 轮**拼成消息（`service.py:107-121, 477-500`）

* 只留 5 轮：控制 token 和成本，客服场景上下文通常很短

* **不做摘要压缩**：省一次 LLM 调用，且摘要可能把温度、价格、克重这类关键数字改写丢掉 —— 这是食品安全场景不能接受的

* MySQL 不可用时降级为无历史，不影响主链路

## 综合题

### ★ Q25. MySQL / Redis / ParadeDB / 云 API / LLM 全挂了会怎样？



* 降级矩阵，且**终点统一是转人工话术、绝不向前端抛技术错误**：



  * MySQL 挂 → FAQ 下线、无历史，直接走 RAG

  * Redis 挂 → 直查 MySQL、embedding 跳过缓存直连（变慢）

  * ParadeDB 挂 → 检索空 → 低置信 → 转人工

  * **SiliconFlow 挂（第二版新增，已做故障注入实测）**：embedding 失败 → 降级**纯 BM25 单路召回**；rerank 失败 → 用 RRF 排名映射 0.5~0.85 兜底分。两故障同时注入时问答仍正常返回，日志 `embedder_failed_bm25_only` / `sf_failed_degrade_rrf`

  * LLM 挂 → 策略选择兜底 DIRECT、生成节点捕获异常转人工

  * 分类器挂 → 降级为专业问题走 RAG

* 旁路动作（落历史、入 pending）失败只记日志，不挡主链路

### Q26. 新增文档 / 换 embedding 模型，向量怎么处理？



* 幂等：入库走 `INSERT ... ON CONFLICT (id) DO UPDATE`（psycopg3 `executemany`），文档与块用稳定内容 ID，重复入库不膨胀

* 只加文档（模型不变）→ 增量 upsert

* **换 embedding 模型或改分块策略 → 必须全量重建**：向量空间 / 维度变了，混存是 "静默错误"—— 不报错但结果全错，比崩溃危险。第二版已实操一次：本地 512 维切云端 bge-m3 1024 维，`init_pg.py --force` 重建（vector 列维度写死在建表语句）→ 全量重灌 82 块 → 四题回归全过才算切完

* 云端 embedding 还有内容哈希两层缓存（进程内 + Redis），重建后新后端用独立命名空间，不会读到旧向量

### ★ Q27. RAGAS 评估那几个数字怎么解释？



* 15 题走**真实链路**：全量 faithfulness 0.730 /relevancy 0.645 /precision 0.655 /recall 0.678；**有检索语料的 13 题 faithfulness 0.843**

* 差距来自 3 道知识库本就没有语料的题：系统**正确转人工**被指标记 0——**这是红线生效的证明，不是故障**（必说）

* 核心 7 题（价格 / 保质期 / 加热 / 冷链 / 健康证 / 采购）faithfulness 全是 1.00

* 评估最大价值：定位了两个改进项 —— 表格专用切分、检索实体校验闸门

* 注意口径：这组数字是**第一版（Milvus + bge-m3 1024）基线**；第二版 ParadeDB 链路的四题功能回归已全过（含红线题），RAGAS 全量复跑排在换云端后端稳定观测之后

### ★ Q28. 这是课程项目吗？哪些是课程教的、哪些是你改的？



* 坦诚：骨架跟着课程 RAG 章节搭（双塔召回 + 稀疏双路、CrossEncoder、意图分类、MCP），但每一层的具体选型都按部署约束换过

* 自己的改动，每处都由场景触发：

  ① **砍掉联网兜底**（不能搜来源不可控的答案）

  ② **低置信不调 LLM、固定话术转人工**

  ③ **不做摘要压缩**（数字不能被改写）

  ④ 分块改为 md 按标题切 + 父子分块 + 可选 Contextual RAG

  ⑤ **新增课程没有的 FAQ 热路径**（BM25+MySQL+Redis，命中零 LLM）

  ⑥ 自己跑了 RAGAS 评估

  ⑦ **第二版轻量化（最大的自主改动）**：Milvus+etcd+MinIO 三件套 → ParadeDB 单容器；自写 RRF 把双路融合下推成一条 SQL；embedding/reranker 做成**本地模型 / SiliconFlow 双后端 + 两级缓存 + 故障降级**；触发场景很具体——目标服务器只有 2核4GB，本地 embedding 还特意从 bge-m3 换成 95MB 的 bge-small-zh，整套链路 CPU 可跑

* 加分句："判断项目是不是自己的，不看骨架从哪来，而看能不能说清每处改动为什么。"

### Q29. 内部配方这种商业机密，工程上怎么保证不被套出来？



* 三层：① 物理隔离 —— 配方只放 `docs/`；② 代码硬拦截 —— 建库脚本 `if "docs" in resolved.parts: raise`；③ 扫描根唯一 —— 只扫 `data/`

* 提示词层再补一道：禁止泄露配方、成本、底价

* 后续：角色权限是上线阻塞项 —— 加盟商可见批发价 / 加盟政策，终端顾客不可见；当前两类用户共用库、无鉴权

### Q30. 已知不足和后续规划（主动说比被问出来强）



* `franchise_data/` 语料仍偏少（82 块中仅 9 块），部分加盟类问题还会转人工

* 长价目表被子块切散，拖低 context\_recall（第一版 0.678）→ 规划按表格行建 chunk

* 阈值现状：FAQ 0.85 是精确率先验；置信闸门 0.45 做过小样本探针标定但缺标注集；RRF 无参数（k=60 为惯例值），weighted_rrf 权重 0.6/0.4 未做对比实验

* 缺检索实体校验闸门、缺角色鉴权

* FAQ 规划扩到 150+；云端后端的长期稳定性（限流、延迟）待生产观测；第二版 RAGAS 基线待复跑
