# RAGAS 评估报告（DeliRAG 重构版 · 2026-10-09）

> 评估对象：重构后 LangGraph 分层架构的 RAG 通道（FAQ 通道不参与本评估）
> 链路：BGE-M3 混合检索（稠密 HNSW 0.7 + 稀疏 0.3）→ bge-reranker-large 精排 →
> 512/64 切分上下文 → SYSTEM_PROMPT + RAG_ANSWER_PROMPT 生成；低于 0.45 置信度固定转人工
> 评估器：`qwen3.7-plus`（LLM）+ `qwen3.7-text-embedding`（嵌入），同一专属实例端点
> 样本：15 题（产品价格 / 保质期 / 食品安全 / 冷链 / 采购 / 品牌 / 加盟 / 报损）

---

## 一、总览（两轮运行按题合并后的稳健基线）

评估器 qwen3.7-plus 是**推理模型**，做 faithfulness 的"陈述抽取"时输出格式会漂移，
单轮会出现一批无事实陈述导致的 NaN；故同日连跑两轮，按题合并
（首轮值优先，NaN 用次轮补齐；两轮均 NaN 的"转人工"题记 0）。

| 指标 | 全量 15 题 | 有检索语料的 13 题 | 含义 |
|---|---|---|---|
| **faithfulness** 忠实度 | **0.730** | **0.843** | 答案是否只基于检索内容（幻觉检测） |
| **answer_relevancy** 相关性 | **0.645** | **0.745** | 答案是否切题 |
| **context_precision** 精确率 | **0.655** | **0.679** | 检索到的内容有多少真正有用 |
| **context_recall** 召回率 | **0.678** | **0.757** | 标准答案所需信息有没有被检回 |

两组口径的差别就是第 12（品牌名）、14（加盟政策）两题——知识库里**根本没有对应语料**，
检索 0 块、系统按红线转人工。它们属于"拒答类"题，放全量里会把四个指标一起拉低。

## 三、关键发现

### 发现 1：有语料题忠实度 0.843，核心问答 7 题全部 1.00

题 1/2/3/7/9/10/13（产品价格、保质期、加热、冷链、健康证、晨检、采购）
faithfulness 全是 1.00、相关性 0.94+，说明"混合检索 + 精排 + 严格只依据知识库生成"的
主链路是可靠的，价格/温度/时长等关键参数零编造。

题 6（常温能放多久）是忠实度设计的正面样本：上下文只有通用温区规范、没有各品项
常温时限，模型没有瞎编保质期，而是给规范 + 声明"具体时限需业务确认"。
RAGAS 因此给 relevancy 0，但这正是食品安全红线要求的行为——**宁可不答，不可错答**。

### 发现 2：context_precision 0.68 是最大短板，根因是长表格切分

低分集中在**价目表类大表格**（题 4/5/13）：
- 手册里"荤菜卤味批发价目表"是 40+ 行的 markdown 表格，512 字切分会把
  相邻品类（水产/素菜/牛腱/猪耳）切进同一块或拦腰切断；
- 稠密 + BM25 会把含同名计量单位、相邻行的块召回，精排后 precision 被稀释
  （题 4 检回 3 块但只有 1 块相关，题 5 干脆检到素菜/水产区域）。

**改进方向**：① 表格类文档识别后用"按行 + 表头前缀"切分（每 N 行重复品类表头）；
② 价目表按品类拆成独立小文档/小 chunk；③ 检索侧加"问题关键实体必须出现在块中"的硬闸门。

### 发现 3：低分里有 3 道是"正确拒答"，属指标适用边界而非系统缺陷

题 12（品牌名）、14（加盟费）、15（报损方法）知识库里没有语料，
系统置信度 0.0、固定回复"信息不足，请联系人工客服 13112345678"并入 knowledge_pending 队列。
RAGAS 对"无上下文 + 拒答"这种答案形态打全 0（faithfulness 常直接 NaN）：
它看不到"知识库没有就该拒答"才是正确行为。面试讲分时要主动给"有语料 13 题"的对照值。

### 发现 4：语料覆盖是内容侧短板（不是算法问题）

- `data/franchise_data/` 是空目录，加盟类问题必然转人工；
- 品牌名、常温陈列时限、报损 SOP 在现有 4 份文档里缺失（部分文档本身标注
  "待业务方访谈后填写"）；
- 内部配方/克重在 `docs/` 中且**物理隔离永不入库**，对应提问被正确拦截。

补齐访谈资料后这些题的指标会自然回升，不需要改算法。

## 四、复现方式

```bash
# 1) 中间件就绪后重建集合并入库（见 scripts/init_milvus.py、build_knowledge_base.py）
# 2) 跑真实链路生成 answer 与 retrieved_contexts（15 题，强制走 RAG 通道）
python scripts/evaluation/build_eval_data.py
# 3) RAGAS 四指标评分（约 5 分钟/轮）
python scripts/evaluation/rag_as.py
```

- 数据四元组（question / answer / retrieved_contexts / ground_truth）在
  `rag_evaluate_data.json`；逐题分数在 `ragas_result.csv`；合并基线在 `ragas_summary.json`。
- 评估器与生成器同为 qwen3.7-plus（非完全独立，属局限）；
  `answer_relevancy.strictness=1`（兼容端点不支持 n>1，鲁棒性略降）。
- ⚠️ 本轮评估后该 API key 对 qwen3.7-plus 返回 `AccessDenied.Unpurchased`
  （免费/授权额度耗尽），复跑前需先更换有效 key 或购买授权。

## 五、改进清单（按性价比排序）

1. **长表格专门切分 + 品类拆文档**（针对发现 2）：预计 precision 提到 0.9、recall 0.85+
2. **检索实体硬闸门**：问题关键实体（如"牛腱"）不出现在块中时降权/转人工
3. **补语料**：加盟政策、品牌问答、常温陈列时限、报损 SOP（业务方访谈后排版入库）
4. **评估器换稳定的非推理模型**（授权恢复后用 qwen-turbo/flash），消除 faithfulness NaN
5. **评估集扩到 50 题并按类型分组统计**（产品/安全/运营/拒答分开，均值不再掩盖差异）
